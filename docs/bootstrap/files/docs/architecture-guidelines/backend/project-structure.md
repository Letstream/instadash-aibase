# Backend Project Structure

> Standard repository layout and module organization for a Django + DRF backend.
> Every backend service should look like this so any engineer can move between projects
> without relearning where things live. The runnable reference implementation is the
> [backend scaffold](../../bootstrap/scaffold/backend/README.md). See [apps-architecture](apps-architecture.md),
> [configuration-and-settings](configuration-and-settings.md).

---

## 1. Repository layout

The backend is its **own git repository**. Inside it, all Python lives under a single `app/`
working directory so that `manage.py`, the settings package, and the apps package sit together
and the Docker build context is small and predictable. The Django project package is always named
**`app`** (so `DJANGO_SETTINGS_MODULE=app.settings`, `celery -A app`, `app.asgi:application`).

```
<project_slug>-backend/
├── app/                          # working dir — everything runs from here
│   ├── manage.py                 # generated by `django-admin startproject app .`
│   ├── pyproject.toml            # Poetry deps + tool config (black/ruff/codespell/coverage)
│   ├── poetry.lock
│   ├── poetry.toml               # in-project venv config (.venv lives here)
│   ├── pytest.ini  conftest.py   # test bootstrap + shared fixtures (see testing.md)
│   ├── Makefile                  # thin wrappers over `poetry run …` (local == CI)
│   ├── .env.example              # every env key, placeholders only (committed)
│   ├── .env                      # real local values (gitignored)
│   ├── app/                      # the Django project package (config, not features)
│   │   ├── __init__.py           # exposes celery_app
│   │   ├── settings/             # split settings package (see configuration-and-settings.md)
│   │   ├── urls.py               # root URLconf; includes each app under its prefix
│   │   ├── celery.py             # Celery app bootstrap
│   │   ├── storage_backends.py   # S3 static/public/private storage classes
│   │   ├── routers.py            # optional DB routers (analytics DB, read replica)
│   │   └── asgi.py / wsgi.py
│   ├── apps/                     # ALL apps live here, namespaced apps.<name>
│   │   ├── __init__.py
│   │   ├── core/                 # shared base classes (see core-app-reference.md)
│   │   ├── accounts/             # identity: user model, auth, tokens
│   │   ├── organization/         # tenancy — multi-tenant projects only
│   │   └── <feature>/            # one cohesive concern per app
│   └── templates/                # optional project-level templates
├── Dockerfile                    # build recipe (see containerization-and-deployment.md)
├── .dockerignore
├── VERSION                       # single source of truth for the release/image tag
├── build.sh / push-image.sh
├── .gitlab-ci.yml  (or)  bitbucket-pipelines.yml  (or)  .github/workflows/
└── README.md
```

**Rules**
- The **project package** (`app/app/`) holds *configuration only* — settings, URL wiring,
  Celery, DB routers, storage. No business logic, no models.
- **All apps** live under `apps/` and are referenced with the dotted, namespaced path
  `apps.<name>` in `INSTALLED_APPS`. Never place an app at the repo root.
- A plain-text `VERSION` file at the repo root is the authoritative version — consumed by the
  image tag, CI, and the running app (surfaced in every API response and to error monitoring).
  Keep it decoupled from the Poetry `version` field.
- Every module that can hold comments starts with the project **license header** (generated
  modules too, except migrations) — see the [scaffold README](../../bootstrap/scaffold/backend/README.md#license-header).

## 2. The project package (`app/app/`)

| File | Responsibility |
|------|----------------|
| `__init__.py` | Import and expose the Celery app so `@shared_task` binds to it: `from .celery import app as celery_app`. |
| `settings/` | Split settings package selected by an `ENVIRONMENT` env var. See [configuration-and-settings](configuration-and-settings.md). |
| `urls.py` | Root URLconf. `include()`s each app under `/api/<app>/` + namespace (proxies forward only `/api/` and `/ws/`), exposes `/api/health/`, registers global error handlers → the core envelope views, mounts API docs **only when `DEBUG`**, and puts the Django admin on an **obfuscated path from env** (`ADMIN_URL`). |
| `celery.py` | Create the Celery app, `config_from_object("django.conf:settings", namespace="CELERY")`, `autodiscover_tasks()`. |
| `storage_backends.py` | S3 storage classes (`StaticStorage`, `PublicMediaStorage`, `PrivateMediaStorage`) plus `private_storage()` / `public_storage()` callables models use. See [storage-and-media](storage-and-media.md). |
| `routers.py` | Optional DB routers — e.g. route an analytics/time-series app to a separate connection; optional read-replica read splitting. |
| `asgi.py` / `wsgi.py` | Standard entrypoints; both `setdefault("DJANGO_SETTINGS_MODULE", "app.settings")`. ASGI is the default (it also serves Channels when a project opts in — see [realtime-channels](realtime-channels.md)). |

## 3. App map — one cohesive concern per app

Split the domain into small apps, each owning **one** concern. Do not pile unrelated models
into one app. A typical service has two tiers of apps:

**Foundational apps** (copied from the scaffold, almost unchanged between projects):
- `core` — abstract base models (`TimeStampedModel`, `UUIDTimeStampedModel`), base API views,
  the `LetstreamAPIRenderer` envelope, exception handling + error codes, permissions, the
  `SecurityEvent` audit table, reusable serializer fields, shared utilities. **No domain models.**
- `accounts` — the custom `User` model, opaque token authentication, credential flows.
- `organization` — **multi-tenant projects only**: `Organization`, the `OrganizationUser`
  membership join, `OrganizationRole` permission codes, invitations, and the abstract
  `OrgScopedModel` every tenant model extends. Single-tenant projects don't have this app — see
  [multi-tenancy §0](multi-tenancy.md#0-single-tenant-vs-multi-tenant).

**Project-specific feature apps** — one per domain concern (e.g. `orders`, `catalog`,
`billing`, `stats`). Each is self-contained and follows the standard app layout in
[apps-architecture](apps-architecture.md).

In `INSTALLED_APPS`, **group and comment** these tiers (Django contrib → third-party →
foundational apps → feature apps) so the split is visible at a glance.

## 4. Scaffolding — use Django commands, never hand-write

- **Create apps with the CLI:** `python manage.py startapp <name> apps/<name>` (create the
  directory first; each app in its own dir under `apps/`). During bootstrap, before the settings
  package exists, use the equivalent `django-admin startapp <name> apps/<name>`. Never hand-author
  `apps.py` / boilerplate — generate it, then edit.
- **Generate migrations with the CLI:** `makemigrations <app>` — never hand-write a migration.
  Review the generated file, then `migrate`. Foundational order: `core` → `accounts` →
  `organization` → feature apps.
- In each app's `apps.py`, set the dotted `name`, an explicit short `label`, and wire signals /
  audit registration in `ready()`:
  ```python
  class OrdersConfig(AppConfig):
      default_auto_field = "django.db.models.BigAutoField"
      name = "apps.orders"
      label = "orders"

      def ready(self) -> None:
          from auditlog.registry import auditlog

          from . import signals  # noqa: F401
          from .models import Order

          auditlog.register(Order, exclude_fields=["modified_on"])
  ```

## 5. Versioned public API (when you expose one)

Keep **internal** app URLs unversioned and app-prefixed (`/api/<app>/…`). Isolate any **externally
consumed** API under its own versioned package so it can evolve independently:

```
apps/<api>/
  urls.py                 # include("apps.<api>.version.v1.urls")
  version/
    v1/
      urls.py  views.py  serializers.py  tests/
```

`v1` views may thinly re-expose the same view classes from feature apps under stable, versioned
route names. Add `v2/` beside `v1/` when the contract changes — never break `v1`.
